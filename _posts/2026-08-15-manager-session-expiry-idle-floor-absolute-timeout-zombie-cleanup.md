## 개요

매니저 세션이 Redis에 만료 없이 무한 누적되는 문제를 해결한다. 유휴 만료를 끄면(`maxIdleTime=0`) 세션을 끝낼 수단이 완전히 사라지는 구조를, **유휴 만료 하한(12시간) + 절대 만료(24시간)** 두 축으로 정비한다. 더불어 계정 삭제 시 세션 폐기 누락과 업로드 조회의 검사 우회를 보완하고, 이미 쌓인 좀비 세션을 1회 정리한다.

## 실측 현황 (조사 시점)

| 서버 | 세션 수 | TTL | 최고(最古) 발급 | maxIdleTime | useSingleLogon |
|---|---|---|---|---|---|
| 개발 서버 | 1345 | 전부 -1 | 2026-04 | 0 | false |
| 한 고객사 운영 | 43 | 전부 -1 | 2026-04-02 | 0 | false |

- 개발 서버의 세션 역인덱스는 멤버 1055개까지 성장.
- 용량은 문제가 아님(개발 서버 4.47MB). 문제는 이 토큰들이 **전부 인증에 통과한다**는 점.
- 실증: 개발 서버에 `isActive=false`인 `super_admin` 계정의 세션 7개가 `role=super_admin`을 그대로 들고 유효 상태로 잔존.
- 고객사 운영 서버의 43개 중 30개는 `role` 필드가 없는 구버전 세션 → 기본값 `admin`으로 처리됨.

## 원인

"자동 로그아웃 시간을 0으로 해도 로그아웃된다"는 이전 버그를 수정하며, `ttl <= 0`이면 기본값(10분)을 쓰던 것을 `ttl == 0`이면 `persist()`(TTL 제거)로 변경했다. 요구 자체는 타당했으나 **유휴 만료를 끈 뒤 세션을 지울 대체 수단이 없다**는 점이 함께 검토되지 않았다.

세션이 사라지는 경로 4개의 당시 상태:

```
유휴 TTL 만료       → 꺼짐 (maxIdleTime = 0)
단일 로그인 정책     → 꺼짐 (useSingleLogon = false)
명시적 로그아웃      → 관리자가 버튼을 눌러야만 동작
계정 비활성화/삭제   → 비활성화만 동작, 삭제는 미처리
```

브라우저를 닫고 떠나면 어디에도 걸리지 않는다.

**기본값 서버도 안전하지 않다.** 설치 시딩값은 `maxIdleTime=3600`이지만, manager-web이 1시간 주기로 무조건 API를 호출하므로 탭이 열려 있는 한 유휴 타이머가 계속 리셋된다 → 사실상 무한. 또한 `maxIdleTime=0`이면 클라이언트 측 자동 로그아웃도 `secondsRef.current > 0` 조건에 걸려 함께 비활성화된다. **서버·클라이언트 양쪽 모두 세션을 끝낼 수단이 없는 상태.**

## 개선안 — 성격이 다른 두 축으로 분리

```
유휴 만료 = maxIdleTime > 0 이면 그 값, 0이면 12시간   ← 요청이 오면 리셋
절대 만료 = 발급 후 24시간                             ← 요청이 와도 리셋되지 않음

실제 TTL = min(유휴 만료, 절대 만료까지 남은 시간)
```

발급 시각은 세션 해시의 기존 `time` 필드를 그대로 쓴다(생성 시에만 기록되고 이후 갱신되지 않음). 새 필드는 불필요.

### 각 축이 막는 것

| 상황 | 유휴만 | 절대만 | 둘 다 |
|---|---|---|---|
| 브라우저 닫고 떠남 | 12시간 정리 | 24시간 방치 | 12시간 정리 |
| 탭만 열어둔 PC(1시간 폴링) | 영구 | 24시간 정리 | 24시간 정리 |
| 탈취 토큰(공격자가 계속 갱신) | 영구 | 24시간 차단 | 24시간 차단 |

### 수치 근거 (12시간 / 24시간)

초안은 7일/30일이었으나 리뷰에서 하루 단위로 단축했다.

- 매니저 토큰은 로그인 권한에 그치지 않고 LiveCMD·원격제어 등 **에이전트 명령까지 도달**한다. 탈취 시 영향 범위가 일반 관리콘솔과 다르다.
- 실제 침해는 비밀번호 크래킹보다 "열어둔 채 퇴근한 매니저 화면"을 그대로 사용하는 형태가 많다. 이 시나리오에서 며칠은 지나치게 길다.
- 개발 서버는 재배포가 잦아 세션이 자주 끊기므로, 짧은 상한의 개발 편의 손실이 크지 않다.

`maxIdleTime=3600` 서버는 평소 동작이 지금과 동일하며 24시간 상한만 추가된다.

## 주의사항 / 리뷰 포인트

**이미 쌓인 좀비는 코드로 사라지지 않는다.** TTL 재계산은 `refresh_ttl()`이 실행돼야 이뤄지고, 그건 해당 토큰으로 요청이 들어와야만 발생한다. 방치된 세션은 요청이 영영 오지 않으므로 TTL=-1로 남는다. 따라서 1회 정리 작업이 코드 수정과 별개로 반드시 필요하다.

**만료 검사를 우회하던 경로가 있었다.** `upload.py`만 `exists()`로 키 존재만 확인해, TTL 없는 레거시 세션이 나이와 무관하게 통과했다. 같은 실수를 유도하지 않도록 `exists()` 자체를 제거했다.

**운영 영향 — 매니저는 최소 하루 1회 재로그인.** 절대 24시간이므로 작업 중에도 하루에 한 번은 끊긴다. 만료 임박 경고나 재로그인 후 화면 복귀가 없어 갑작스러운 401로 체감되므로, 고객사 안내 또는 프런트 보완이 필요하다.

**수치는 하드코딩.** `IDLE_FALLBACK_SECONDS` / `ABSOLUTE_MAX_SECONDS`는 설정으로 조절할 수 없다. 운영자가 끌 수 있으면 안전장치의 의미가 없기 때문이다. 조절이 필요해지면 하한을 둔 설정값(0 불가)으로 여는 방향을 검토한다.

API 스펙 변경은 없다 — 요청/응답 스키마 불변.
