## 개요

한 고객사 회의에서 "프로세스 영향도 오류"로 보고된 증상의 근본 수정이다. 노드 삭제 API가 프로세스 raw만 지우고 **노드 축 집계**를 남겨, 삭제된 노드가 화면에 영구 잔존했다. 게다가 raw가 사라져 SUID(프로세스 식별자) meta 조회가 404를 냈다. cascade 보강 + 인덱스/고아 정리 migration + meta 조회 fallback 세 축으로 해결했다.

## 기존 vs 변경 흐름

```
[기존] 노드 삭제
  cascade: detect/timeline/report/upload/sprocess(raw)/filelist/nodeinfo
  → 노드 축 집계(hourly/daily) 미삭제 (TTL 도 없음)
  → 노드 축 위젯에 "(알 수 없음)" 노드 영구 잔존
  → 삭제 노드 배타 SUID: 집계엔 남는데 raw 없음
     → GET .../{suid}/meta 가 raw 만 조회 → 404

[변경] 노드 삭제
  cascade: ... + sprocess raw → 노드 축 집계 순서 고정 삭제
    (집계를 먼저 지우면 집계 데몬 partial/late pass 가 남은 raw 를
     $merge 로 재집계해 행이 영구 부활 — 순서가 정확성 조건)
  meta 조회: raw(범위) → raw(범위 무시) → hourly → daily 내장 meta → 404
```

## 핵심 — 왜 순서가 정확성 조건인가

가장 중요한 부분이 삭제 순서다. **raw를 먼저 지우고 집계를 나중에 지운다.** 역순이면 집계 데몬(매시 partial, 10분 주기 partial, 120시간 late pass)이 아직 남아 있는 raw를 `$merge`로 다시 집계해 방금 지운 행을 되살린다. 그러면 삭제된 노드가 영구히 부활한다.

이건 분산 집계 파이프라인에서 흔히 놓치는 함정이다. "지우면 끝"이 아니라, 지운 원본을 근거로 파생 데이터를 재생성하는 백그라운드 작업이 돌고 있다면, **파생부터 지운 뒤 원본을 지우면 그 사이에 파생이 되살아난다.** 원본을 먼저 끊어야 재생성의 근거가 사라진다.

집계는 두 축이 있는데, 삭제 대상을 정확히 골랐다.

- **노드 축 집계**(node_id 키·TTL 없음): 삭제된 노드가 곧 잔존물이므로 cascade로 삭제한다.
- **SUID 축 집계**(노드가 뭉개진 전사 통계): 특정 노드만 도려낼 문서가 없고 TTL(90/365일)로 자연 소멸하므로 의도적으로 제외한다.

## meta 조회 fallback

meta는 "이 SUID가 뭐였나"를 답하는 **정체성 조회**다. 존재 판정이 아니므로, 범위 안의 raw가 없다고 404를 내면 안 된다. 그래서 체인을 재구성했다.

1. raw (범위)
2. raw (범위 무시, 전체 필드 우선)
3. hourly 집계 내장 meta
4. daily 집계 내장 meta
5. 그래도 없으면 404 (존재한 적 없는 SUID — 프론트 오호출 노출)

응답 스키마 필드는 전부 기존 optional이라 프론트 수정이 필요 없다. raw 전용 필드는 집계 fallback 시 null로 채운다.

## 인덱스 + 고아 정리 migration

- **노드 축 인덱스**: node_id·시간키 2종을 추가하고, 이미 삭제된 노드가 남긴 고아 행을 1회 소급 삭제했다. 수정 이전 경로(구 삭제 API)로 생긴 것까지 포함한다.
- **daily 인덱스**: (SUID, day_start) — fallback·404 경로가 무TTL 대형 컬렉션을 COLLSCAN하지 않도록. 예전에 "필요 없다"고 판단해 안 만들었던 전제가 뒤집혔다.

## 리뷰 포인트

- **배포 순서**: rest-api 배포 전에 migration이 먼저 돌아야 한다. migration이 스킵된 채 API만 갱신되면 삭제/404 경로가 무TTL 대형 컬렉션 COLLSCAN이 된다.
- **수용한 잔여 한계**: ① 데몬 in-flight 파이프라인과의 미세 race로 드물게 고아 행이 생길 수 있다 — 실발생 관측 후 주기 sweep을 검토한다. ② 레거시 삭제 API는 여전히 cascade가 없다(레거시 수정 최소화 정책). ③ 삭제 노드 배타 SUID의 상세 drill-down은 빈 결과다 — meta 헤더만 fallback으로 답한다.

## 검증

단위 테스트 12건을 신규 추가(전체 1,479건 통과)했고, 실제 mongod에서 행위를 검증했다 — migration 멱등성, 고아만 삭제, explain으로 인덱스 사용 확인, fallback 7개 시나리오. 여기에 다각도 적대 리뷰 2회를 더했다.

핵심 교훈은 하나다. 파생 데이터를 재생성하는 백그라운드 작업이 있는 시스템에서 삭제를 구현할 때는, **삭제 순서 자체가 정확성 조건**이 된다. 원본을 먼저 끊지 않으면, 지운 것이 되살아난다.
