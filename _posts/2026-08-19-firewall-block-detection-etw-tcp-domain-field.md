## 개요

윈도우 방화벽으로 나가는 연결을 막아도 에이전트가 증상을 만들지 못했다. 이걸 고치고, 관련 TCP 룰 설명도 같이 정리했다.

찾아보니 방화벽만의 문제가 아니었다. PC 영역 증상 세 가지(방화벽 차단, 커널 자원 부족, 임시 포트 고갈)가 전부 룰까지 가지 못하고 있었다.

## 원인

TCP ETW 처리 코드에서 룰 매칭 바로 앞에 이 검사가 있었다.

```cpp
if (!json.isMember("Info") || !json["Info"].isMember("Domain")) {
    return;
}
```

그런데 `Info["Domain"]`을 넣는 case와 안 넣는 case가 갈려 있었다.

| 구분 | EventID |
|---|---|
| 넣음 | 1002, 1033, 1034, 1040, 1045 |
| 안 넣음 | 1020(방화벽 차단), 1030(커널 자원 부족), 1050(포트 고갈) |

안 넣는 세 개가 전부 PC 영역 증상이었다. 룰 정의에 `TCP_LOCAL_FIREWALL_BLOCK` 같은 룰이 다 들어 있었지만, 그 앞의 Domain 검사에서 걸러져 쓰이질 못했다.

타임아웃이나 연결 거부·리셋은 Domain을 넣으니까 잘 돌아가고 있었다. 다른 노드에서 TCP 증상이 정상적으로 잡히던 게 그래서였다. 그래서 "일부는 되는데 방화벽 차단만 안 되는" 형태로 결함이 가려져 있었다.

## 확인한 것

ETW 트레이스로 직접 관측했다.

- 윈도우 방화벽으로 나가는 연결을 막으면 커널이 1020(`TcpConnectTcbFailedInspect`)을 낸다.
- 이벤트 본문의 ProcessId는 0으로 오는데, ETW 헤더 PID는 실제 연결한 프로세스와 같다. 헤더 폴백이 제대로 동작한다.
- 막히면 연결 실패까지 0ms다. PC 밖으로 나가지 않았다는 뜻이다.
- 에이전트 ETW 세션은 멀쩡했다. TCPIP 공급자가 붙어 있고 Level 5, 손실 버퍼 0, 실시간 모드였다. 세션 문제는 아니었다.

## 고친 내용

`case 1020 / 1030 / 1050`에도 1045가 하던 대로 Domain을 채워 넣었다.

```cpp
ip      = ExtractIP(remoteAddr);
domain  = LookupDomain(ip);
...
info["Domain"] = domain;
```

`LookupDomain`은 DNS 캐시에 없으면 IP를 그대로 돌려주니까 빈 값이 될 일이 없다. 고치고 다시 돌려보니 콜백부터 job 넣는 데까지 다 통과했고, 매니저 화면에도 증상이 떴다.

## 교차검증에서 나온 후속

1020은 승인됐고, 지적은 하나였다. 1030 / 1050은 RemoteAddress가 비어 있으면 Domain 검사보다 먼저 `IsSkipIpFast`에서 걸린다. 목적지와 무관한 PC 증상까지 잡으려면 따로 처리가 필요하다. 실제로 그 이벤트에 주소가 비는지는 후속으로 확인하기로 했다.

## 룰 쪽에서 함께 정리한 것

**1. 방화벽 룰이 묻히는 문제.** 1020의 Status가 `0xC0000022(STATUS_ACCESS_DENIED)`다. 룰 정의에서 `STATUS_ACCESS_DENIED` 룰이 `TCP_LOCAL_FIREWALL_BLOCK`보다 위에 있어서 먼저 걸린다. 그래서 방화벽으로 막아도 화면에는 방화벽 룰이 아니라 접근 거부 룰이 떴다. `TCP_LOCAL_FIREWALL_BLOCK`은 `Info.Category`라는 더 확실한 근거를 보는 룰이니 순서를 위로 올렸다.

**2. 설명 문구.** "내 PC의 보안 소프트웨어 또는 시스템 정책이 … 차단했습니다"를 "내 PC의 방화벽 또는 보안 소프트웨어가 … 차단했습니다"로 바꿔, 방화벽이 원인일 때 사용자가 바로 이해하도록 했다.

**3. 제목 크기가 뒤집혀 있던 문제.** Detail에서 `#`를 소제목으로 쓰고 있었다. `#`가 가장 큰 제목이라 화면에서 소제목이 제목(`##`)보다 크게 나왔다. 소제목으로 쓴 `#`를 `####`로 내렸고, 이건 TCP 말고 다른 룰 파일도 다 해당돼서 한번에 조정했다.

**4. 영역 표시가 문서와 다른 룰.** 몇몇 룰의 영역 구분이 실제 프로토콜 동작과 어긋나 있었다.

| 룰 | 화면 | 실제로 맞는 것 |
|---|---|---|
| STATUS_PORT_UNREACHABLE | 서버 문제 | 룰이 맞다. ICMP Port Unreachable은 목적지 호스트가 보내는 응답이다. 중간 장비가 막을 때는 통신 금지(코드 13)로 다르다 |
| STATUS_NETWORK_UNREACHABLE | PC 문제 | 룰 쪽이 실제에 가깝다. 랜선 빠짐이나 VPN 전환 같은 단말 문제가 훨씬 흔하다 |
| SLOW_SUCCESS (연결 지연) | 네트워크 문제 | 둘 다 근거가 약하다. 연결 수립 시간은 왕복 시간과 서버 응답 지연이 섞여 나눌 수 없다. 영역 표시를 빼고 "성능 이상"으로 두는 게 맞다 |

## 재현 도구

방화벽 차단을 재현하려고 배치 스크립트 세 개를 만들어 뒀다.

- 연결 점검 — 연결되는지, 얼마나 걸리는지 찍어준다
- 방화벽 차단 등록 — 차단 규칙 등록 (TCP·UDP 443)
- 방화벽 차단 해제 — 원래대로 되돌린다

막기 전후 소요 시간을 비교하면, 연결 실패까지 0ms라는 사실에서 "단말 안에서 막혔다"는 게 드러난다.
